## 2. What I understood
Work orders are kept in `data/work_orders.csv`. Every save rewrites the whole file, so two people saving at once can lose an edit. We move the orders into a SQLite file, `data/fieldops.db`, with a one-time migration script. The five functions in `fieldops/store.py` keep their names and results, so the screens and the nightly job work the same. The CSV file stays on disk as the way back, and a rollback note explains the steps.

## 3. Design decisions
1. Database location: `data/fieldops.db`. An optional `FIELDOPS_DB` environment variable lets tests use a temp file. Without it, the real path is used. Answer: default. Changes: `store.py` reads the variable; tests never touch real data.
2. Migration when the database already exists: stop with a clear message and change nothing. The user deletes the file to re-run. Answer: default. Changes: `migrate.py` refuses to overwrite, so a second run cannot wipe newer orders.
3. Saving: `update_order` changes only that one row in a transaction. `save_orders` replaces all rows in one transaction. `crews.csv` and `load_crews` stay as they are. Answer: default. Changes: assign and close no longer rewrite everything.
4. Rollback note: steps at the top of `scripts/migrate.py`: stop the app, optionally export the database back to CSV with one `sqlite3` command, restore the old `store.py` from git, run `./run.sh`. No extra export code. Answer: default. Changes: the note is documentation only.

## 5. Acceptance criteria
- Running `python scripts/migrate.py` creates `data/fieldops.db` with every order in it.
- The order count in the database equals the order count in the CSV file.
- `./run.sh` still shows the orders table, and assign and close still work.
- The top of `scripts/migrate.py` has a step-by-step rollback note to the CSV file.
- `data/work_orders.csv` is still there and unchanged after migration.
- Running the migration a second time changes nothing and says why.

## 6. Test plan
All in `tests/test_store.py`, using a temp CSV and a temp database, never real data.
- Migration creates the database and the counts match: `test_migrate_copies_every_order`.
- Orders load with the same fields and types (id and priority are whole numbers): `test_load_orders_matches_csv`.
- Assign and close change only the one order: `test_update_order_changes_one_row`.
- `get_order` returns the order, or none for an unknown id: `test_get_order`.
- `save_orders` replaces all orders: `test_save_orders_replaces_all`.
- The CSV file is unchanged after migration: `test_csv_untouched`.
- A second migration refuses and leaves the database as it is: `test_migrate_refuses_existing_db`.
- Rollback note is the first thing in `scripts/migrate.py`: `test_rollback_note_present`.
- Showing the table in the browser (`./run.sh`) is checked by hand by the requester.

## 7. Work units
- `fieldops/store.py`: read and write orders in SQLite; same five functions.
- `scripts/migrate.py`: one-time CSV to SQLite copy, count check, rollback note at the top.
- `tests/test_store.py`: tests listed above.
- `changes/KAN-158.md`: change log entry.
- `plans/KAN-158.md`: this spec.

## 8. Out of scope
- Moving `crews.csv` to SQLite.
- Deleting `data/work_orders.csv`.
- Changing screens, assign rules, the nightly job or reports.
- Automatic sync from the database back to the CSV file.
- New libraries; only the Python standard library `sqlite3` is used.

## 9. Risk and compliance
- Personal data: orders hold customer names and phone numbers; they are copied as they are and never printed. Scripts and tests print counts only.
- Secrets: none.
- Data loss: migration never overwrites an existing database and never edits the CSV file.
- Rollback: documented at the top of `scripts/migrate.py`; edits made after migration are lost unless exported first.
