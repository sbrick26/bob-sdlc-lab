# KAN-158: Move work orders from the CSV file to SQLite

## 1. Ticket

- Key: KAN-158
- Title: Move work orders from the CSV file to SQLite
- Requester: Swayam Barik
- Link: https://demo-ibm-bob.atlassian.net/browse/KAN-158

## 2. What I understood

Work orders live in `data/work_orders.csv`, and every save rewrites the whole file, so two people saving at once can lose an edit. We move the orders into SQLite (`data/fieldops.db`) with a one-time `python scripts/migrate.py`. `fieldops/store.py` keeps the same five functions, so the screens, assign, close and the nightly job work the same. The CSV file stays in place as the way back, and the top of `scripts/migrate.py` explains how to go back.

## 3. Open questions

1. Crews: the ticket only talks about work orders. Default: `load_crews` keeps reading `data/crews.csv`.
2. Existing tests: `tests/conftest.py` points `store.ORDERS_FILE` at a temp CSV, which will no longer feed `load_orders`. It is not in the ticket's file list. Default: change only that fixture so it also builds a temp database, and add it to the work units.

## 4. Acceptance criteria

- `python scripts/migrate.py` creates `data/fieldops.db` and prints how many orders it copied.
- The database holds 40 orders, the same as the CSV file, including the two orders with no site.
- Running the migration a second time does not wipe or duplicate orders.
- `./run.sh` shows the orders table, and assign and close still work.
- `data/work_orders.csv` is still there and unchanged.
- The top of `scripts/migrate.py` has a numbered, step-by-step rollback note.

## 5. Test plan

All in `tests/test_store.py`, using a temp folder, never the real `data/`.

- Migration creates the database and copies every order: `test_migrate_copies_every_order`.
- Count matches the CSV, including blank-site orders: `test_migrate_count_matches_csv`.
- Second run does not duplicate or wipe: `test_migrate_is_repeatable`.
- The five functions return the same shapes as before (`id` and `priority` are numbers): `test_load_orders_shape`, `test_get_order`, `test_update_order_saves`, `test_save_orders_roundtrip`, `test_load_crews_unchanged`.
- CSV file is untouched by migration: `test_migrate_leaves_csv_unchanged`.
- Rollback note is at the top of the script: `test_migrate_has_rollback_note`.
- "`./run.sh` shows the table, assign and close work": the existing `tests/test_assign.py` must still pass, and I check `./run.sh` by hand in the PR.

## 6. Work units

- `fieldops/store.py`: change. Read and write SQLite instead of the CSV. Same five function names and return shapes.
- `scripts/migrate.py`: create. Copies the CSV into `data/fieldops.db`, safe to run twice. Rollback note at the top.
- `tests/test_store.py`: create. The tests listed above.
- `tests/conftest.py`: change the `temp_store` fixture only (see open question 2).
- `changes/KAN-158.md`: create. Two lines, as the change-log rule requires.

## 7. Out of scope

- Any change to `fieldops/assign.py`, `app.py`, `report.py` or `nightly.py`.
- Deleting or editing `data/work_orders.csv`.
- Moving crews to SQLite.
- A script that exports the database back to CSV. The rollback note lists the steps instead.
- Changing `requirements.txt`. SQLite comes with Python.
- Committing `data/fieldops.db`. `*.db` is git-ignored, so a fresh checkout runs the migration once before `./run.sh`.

## 8. Risk and compliance

- Personal data: orders hold customer names and phone numbers. Copied as is. Tests use made-up values. Nothing is printed to logs or chat.
- Secrets: none.
- Data loss: the migration only reads the CSV and never deletes it. Orders saved after migration exist only in the database, so the rollback note says to export first.
- Rollback: follow the note in `scripts/migrate.py`, then revert `fieldops/store.py`.
