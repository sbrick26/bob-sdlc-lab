## 2. What I understood

Work orders live in `data/work_orders.csv`. Every save rewrites the whole file, so two people saving at once can lose an edit. We move the orders into a SQLite database, `data/fieldops.db`, with a one-time script, `python scripts/migrate.py`. `fieldops/store.py` keeps the same five functions, so the screens, the assign page and the nightly job work as before. The CSV file stays in place as the way back. A rollback note at the top of `scripts/migrate.py` explains how to return to it.

## 3. Open questions

1. Should crews move to SQLite too? Default: no. `load_crews` keeps reading `data/crews.csv`. The ticket only asks for work orders.
2. Should the script export the database back to CSV for rollback? Default: no. The rollback note lists the steps, including an export step to run first if orders changed after the migration. The script does not do it.

## 4. Acceptance criteria

- Running `python scripts/migrate.py` creates `data/fieldops.db` and prints how many orders it copied.
- The database holds 40 orders, the same count as `data/work_orders.csv`. This includes orders 1035 and 1036, which have no site.
- Running the migration a second time does not wipe, lose or duplicate any order.
- `./run.sh` still shows the orders table, and assign and close still work.
- `data/work_orders.csv` is still there and unchanged.
- The top of `scripts/migrate.py` has a numbered, step-by-step note on going back to the CSV file.

## 5. Test plan

All tests go in `tests/test_store.py`. They use a temporary copy of the data, never the real files.

- Migration creates the database and the copied count is printed: `test_migrate_creates_db_and_reports_count`.
- Database count equals CSV count (40), and the no-site orders are present: `test_migrate_keeps_every_order`.
- Second migration run leaves 40 orders, no duplicates: `test_migrate_twice_is_safe`.
- `load_orders`, `get_order`, `update_order`, `save_orders` and `load_crews` give the same results as before, including int `id` and `priority`: `test_store_functions_same_behaviour`.
- Assign and close still work through `fieldops.assign` and the Flask app: `test_assign_and_close_still_work`.
- CSV file is not changed by migration: `test_csv_left_untouched`.
- Rollback note is at the top of the script and has numbered steps: `test_migrate_has_rollback_note`.

Run: `python -m pytest tests/test_store.py -v`. Tests must not print customer names or phone numbers.

## 6. Work units

- `tests/test_store.py`: create. Tests listed above, written first.
- `scripts/migrate.py`: create. Rollback note at the top, then a one-time, re-runnable CSV to SQLite copy. Prints only the count.
- `fieldops/store.py`: change. Same five functions, backed by SQLite. `load_crews` stays on CSV.
- `plans/KAN-158.md`: this plan.
- `CHANGELOG.md`: add one entry at the top.

Nothing else changes. `fieldops/app.py`, `fieldops/assign.py`, `fieldops/report.py`, `fieldops/nightly.py` and `data/work_orders.csv` are not touched.

## 7. Out of scope

- Moving crews to SQLite.
- Deleting or editing `data/work_orders.csv`.
- Automatic export from SQLite back to CSV.
- Changes to the screens, the report or the nightly job.
- New libraries. SQLite comes with the Python standard library.

## 8. Risk and compliance

- Personal data: orders hold customer names and phone numbers. The script and tests never print them. Phone numbers, if ever shown, are masked as 415-555-****.
- Secrets: none. No credentials involved.
- Data loss: migration only reads the CSV. It must not overwrite existing rows on a re-run. `data/fieldops.db` is git-ignored (`*.db`).
- Rollback: keep `data/work_orders.csv`, follow the numbered note at the top of `scripts/migrate.py`, and revert the `fieldops/store.py` change.
