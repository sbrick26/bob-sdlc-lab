## 2. What I understood

The crew assignment rules in `fieldops/assign.py` have no tests. We add tests that record what the code does today, odd parts included. We do not change any behavior. If something looks wrong, we note it in a comment and in the PR description, and we do not fix it. Tests use made-up crews and orders and a temp copy of the CSV files. They never touch the real data.

## 3. Open questions

1. `CHANGELOG.md` is not in the ticket's file list, but our rules require an entry on every PR. Default: add one entry at the top of `CHANGELOG.md`.
2. `pytest` is not in `requirements.txt`, and the ticket says not to change that file. Default: leave `requirements.txt` alone and assume pytest is already installed.

## 4. Acceptance criteria

- `python -m pytest` finishes with no failures.
- Priority 1: a free home crew is picked even when it lacks the skill.
- Priority 2 picks the home crew only if it has the skill. The skill fallback picks the first free crew, in file order, that has the skill.
- An order with no site skips the site rules and goes straight to the skill fallback.
- Unknown equipment, and the case where every crew is busy, both go to crew A.
- No file in `fieldops/` or `data/` changes.

## 5. Test plan

All in `tests/test_assign.py`, with fixtures in `tests/conftest.py`.

- Priority 1 home crew without the skill: `test_priority1_home_crew_wins_without_skill`.
- Priority 2 home crew with the skill: `test_priority2_home_crew_with_skill`.
- Priority 2 home crew without the skill, so fallback applies: `test_priority2_home_crew_without_skill_falls_back`.
- Skill fallback, first free crew in file order: `test_skill_fallback_first_free_crew_in_file_order`.
- Order with no site: `test_no_site_skips_site_rules`.
- Unknown equipment returns A: `test_unknown_equipment_goes_to_default_crew`.
- All crews busy returns A: `test_all_busy_overflows_to_default_crew`.
- Busy crews are skipped (load of 4): `test_busy_crew_is_skipped`.
- `crew_load` counts only assigned orders for known crews: `test_crew_load_counts_assigned_orders_only`.
- `assign_order` writes to the temp CSV, and refuses an unknown crew, a missing order, or a closed order: `test_assign_order_*`.
- "No file in `fieldops/` or `data/` changed": checked with `git status` in the PR, not by a test.

## 6. Work units

- `tests/test_assign.py`: create. The characterization tests listed above.
- `tests/conftest.py`: create. Fixtures that copy made-up orders and crews into a temp folder and point `store.ORDERS_FILE` and `store.CREWS_FILE` at them.
- `CHANGELOG.md`: add one entry at the top (see open question 1).

## 7. Out of scope

- Any change to `fieldops/`, `data/` or `requirements.txt`.
- Fixing the odd behaviors found. They are recorded only. Examples seen so far:
  - Crew A is returned even when A is itself busy.
  - A priority 3 order ignores the site rules.
  - `crew_load` changes the crew dicts it is given.
  - A priority 1 order with no free home crew falls through to the skill fallback.
- Tests for `fieldops/app.py`, `report.py`, `nightly.py` or `store.py` on their own.

## 8. Risk and compliance

- Personal data: none. Tests use made-up orders. No real customer names or phone numbers.
- Secrets: none.
- Data loss: none. `assign_order` writes only to the temp copy, never to `data/`.
- Rollback: delete the two test files and revert the `CHANGELOG.md` entry. No production code is touched.
