# KAN-159 — Let dispatch run work orders by asking in plain words

## 2. What I understood
Dispatch needs to give Bob a plain-English instruction like "show open orders at the North Substation and assign the top two to crew B" and have it executed without touching the web screen. We will add a FastMCP stdio server (`fieldops/mcp_server.py`) that exposes three tools — `list_orders`, `assign_order`, and `close_order` — each delegating entirely to the existing functions in `fieldops/store.py` and `fieldops/assign.py`. No business logic is duplicated. The server is added to `requirements.txt` (`mcp`) and documented in `fieldops/README.md`. A pytest suite in `tests/test_mcp_server.py` covers all three tools using temporary fixture data.

## 3. Design decisions
| # | Question | Answer | Effect |
|---|----------|--------|--------|
| 1 | Status string written by `close_order` | **default** — `"closed"` | Consistent with the guard in `assign.py` line 67 |
| 2 | PII fields in `list_orders` response | **default** — strip `customer_name` and `customer_phone` | Those fields never appear in LLM context |
| 3 | Test data source | **default** — temporary fixture CSV, created and torn down per test | Isolated; no side-effects on live data |
| 4 | Module location | **default** — `fieldops/mcp_server.py`, started with `python -m fieldops.mcp_server` | Matches ticket hint |

## 4. Open questions
None.

## 5. Acceptance criteria
- `list_orders(site, status)` returns only orders matching both filters; response contains no `customer_name` or `customer_phone` fields.
- `assign_order(id, crew)` assigns the given order to the given crew and returns success/failure; the change is visible in `data/work_orders.csv`.
- `close_order(id)` sets the order status to `"closed"`; the change is visible in `data/work_orders.csv`.
- `python -m fieldops.mcp_server` starts without error (stdio transport).
- `python -m pytest tests/test_mcp_server.py` passes with no failures.
- `fieldops/README.md` contains a line explaining how to start the MCP server.

## 6. Test plan
All tests live in `tests/test_mcp_server.py`. Each test creates a temporary fixture CSV, points `store.ORDERS_FILE` at it, calls the tool function directly, and asserts the result.

| Criterion | Test |
|-----------|------|
| `list_orders` filters by site and status | `test_list_orders_filters` |
| `list_orders` strips PII fields | `test_list_orders_no_pii` |
| `assign_order` updates crew and status | `test_assign_order_success` |
| `assign_order` rejects unknown crew | `test_assign_order_bad_crew` |
| `close_order` sets status to "closed" | `test_close_order` |

## 8. Out of scope
- No changes to `fieldops/store.py`, `fieldops/assign.py`, or any other existing module.
- No authentication or authorisation on the MCP server.
- No changes to the Flask web screen.
- `.bob/mcp.json` configuration is the builder's responsibility only if the ticket explicitly requires it; the ticket says "after it is added" as an instruction to the user, not a code deliverable.

## 9. Risk and compliance
- **PII:** `customer_name` and `customer_phone` are stripped from all MCP tool responses; they are never logged or returned.
- **Secrets:** none introduced.
- **Data loss:** tools write through `store.update_order`; no new file-write paths.
- **Rollback:** delete `fieldops/mcp_server.py` and revert `requirements.txt`; existing web screen is unaffected.
