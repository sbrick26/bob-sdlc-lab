# KAN-159: Let dispatch run work orders by asking in plain words

## 1. Ticket

- Key: KAN-159
- Title: Let dispatch run work orders by asking in plain words
- Requester: Swayam Barik
- Link: https://demo-ibm-bob.atlassian.net/browse/KAN-159

## 2. What I understood

Dispatch wants to type one sentence in Bob, such as "show open orders at the North Substation and assign the top two to crew B", and have it done without the web screen. We add a small MCP server with three tools: list orders, assign an order, close an order. It calls the existing code in `fieldops/store.py` and `fieldops/assign.py`, so the rules are the same as the web screen. "Top" means lowest priority number first, then oldest created date. The server is started with `python -m fieldops.mcp_server`.

## 3. Open questions

1. The ticket says use FastMCP. The current `mcp` package is 2.3.0 and its server class is `MCPServer`. Default: pin `mcp==2.3.0` in `requirements.txt` and use `MCPServer` over stdio. The three tool names stay the same.
2. Customer name and phone are personal data. Default: `list_orders` never returns them.

## 4. Acceptance criteria

- The server offers exactly three tools: `list_orders(site, status)`, `assign_order(id, crew)`, `close_order(id)`.
- `list_orders` returns the orders for that site and status, lowest priority number first, then oldest created date. It shows no customer name and no phone number.
- `assign_order` and `close_order` give the same result as the web screen. An unknown crew, a missing order, or a closed order is refused and nothing changes.
- A change made through the server shows on the web screen, because both read and write the same files.
- `python -m pytest tests/test_mcp_server.py` finishes with no failures, and `python -m fieldops.mcp_server` starts the server.
- `fieldops/store.py`, `fieldops/assign.py`, `fieldops/report.py` and `data/` do not change.

## 5. Test plan

All in `tests/test_mcp_server.py`. They use the existing `temp_store` fixture in `tests/conftest.py`, so the real `data/` is never touched.

- Exactly three tools, with these names: `test_server_offers_exactly_three_tools`.
- Site and status filter, best first (priority, then created): `test_list_orders_filters_and_sorts_top_first`.
- No customer name or phone in the result: `test_list_orders_hides_customer_data`.
- Assign works and is saved to the temp CSV: `test_assign_order_saves_change`.
- Unknown crew, missing order, closed order are refused, file unchanged: `test_assign_order_refusals_change_nothing`.
- Close works and is saved; a missing order is refused: `test_close_order_saves_change_and_refuses_missing`.
- Web screen shows the change (Flask test client on the same temp files): `test_change_shows_on_web_screen`.
- Server starts: `test_module_exposes_main_entry`.
- "Four files do not change": checked with `git status` in the PR, not by a test.

## 7. Out of scope

- Any change to `fieldops/store.py`, `fieldops/assign.py`, `fieldops/report.py` or `data/`.
- Fixing odd behavior in the existing rules. Examples: `assign_order` does not check crew load, and the web screen can close an order that is already closed. The server copies both.
- Extra tools, login for the server, or running it over HTTP.
- Editing `CHANGELOG.md`.

## 8. Risk and compliance

- Personal data: `list_orders` leaves out customer name and phone. Tests use made-up customers.
- Secrets: none.
- Data loss: the CSV is rewritten whole on every save, and two people saving at once can lose an edit (known, noted in `store.py`). The server adds one more way to write, so the risk is a little higher. Not fixed here.
- New package: `mcp` is on the approved list. Pinned to an exact version.
- Rollback: delete the new files, remove the README line and the `requirements.txt` line. No existing code changes.
