## 2. What I understood
Dispatch needs to control work orders by typing natural-language sentences in the IDE instead of using the web screen. We will expose three MCP tools — `list_orders`, `assign_order`, and `close_order` — via a FastMCP stdio server at `fieldops/mcp_server.py`. The tools delegate all business logic to the existing `store.py` and `assign.py` functions. Once the server is wired into `.bob/mcp.json`, Bob can call these tools directly from the IDE, and every change is immediately visible in the web screen.

## 3. Design decisions
| # | Question | Answer | Effect |
|---|----------|--------|--------|
| 1 | Module location for the server | default — `fieldops/mcp_server.py`, started with `python -m fieldops.mcp_server` | Single clear entry point |
| 2 | Strip PII (`customer_name`, `customer_phone`) from `list_orders` response | default — yes, strip both fields | PII never reaches the LLM |
| 3 | `close_order` precondition: only succeed when status is `"assigned"` | default — yes | Prevents closing unassigned or already-closed orders |
| 4 | Pin `mcp` version | default — `mcp==1.30.0` (changed from 1.9.4: 1.9.4 fails to import with the installed pydantic 2.14.1, `eval_type_backport` missing; 1.30.0 is the newest 1.x and still has `FastMCP`) | Reproducible builds |

## 5. Acceptance criteria
- `list_orders(site, status)` returns matching work orders with `customer_name` and `customer_phone` stripped.
- `assign_order(id, crew)` assigns the order to the given crew and returns `true`; returns `false` for an unknown crew or a closed order.
- `close_order(id)` sets status to `"closed"` and returns `true` when the order is currently `"assigned"`; returns `false` otherwise.
- `python -m pytest tests/test_mcp_server.py` passes with no failures.
- After adding the server to `.bob/mcp.json`, the sentence "show open orders at the North Substation and assign the top two to crew B" works end-to-end and the web screen reflects the change.
- `fieldops/README.md` contains a line explaining how to start the MCP server.

## 6. Test plan
All criteria are verified by `fieldops-repo/tests/test_mcp_server.py`:
- Test `list_orders` with a matching site/status — confirm PII fields absent.
- Test `list_orders` with no match — confirm empty list.
- Test `assign_order` with valid id and crew — confirm `true` and order status updated.
- Test `assign_order` with unknown crew — confirm `false`.
- Test `assign_order` on a closed order — confirm `false`.
- Test `close_order` on an assigned order — confirm `true` and status `"closed"`.
- Test `close_order` on an open order — confirm `false`.
- Test `close_order` on already-closed order — confirm `false`.

## 8. Out of scope
- No changes to `store.py`, `assign.py`, or any other existing module.
- No changes to the web screen or Flask app.
- No automatic `.bob/mcp.json` edit (the builder adds that manually after the server is working).
- No authentication or authorisation on the MCP server.
- No ordering/sorting logic beyond what `store.py` already provides.

## 9. Risk and compliance
- **PII:** `customer_name` and `customer_phone` are stripped in `list_orders` before any data leaves the server. They are never logged.
- **Secrets:** None required by this server.
- **Data loss:** The server calls `store.update_order` which rewrites the CSV; concurrent writes remain unprotected (pre-existing limitation, out of scope).
- **Rollback:** Remove `mcp_server.py` entry from `.bob/mcp.json` to disable the tools without touching other code.
