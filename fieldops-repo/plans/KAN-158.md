# KAN-158: Move work orders from the CSV file to SQLite

## 2. What I understood

Work orders live in `data/work_orders.csv`. The whole file is rewritten on every save, so two people saving at once can lose an edit. We move work orders to a SQLite database, `data/fieldops.db`, using a one-time migration script. The functions in `fieldops/store.py` keep the same names and behaviour, so the web screens, assign, close, the nightly job and the report work as before. The CSV file stays in place as the way back. Crews stay in `data/crews.csv`.

## 3. Design decisions

1. Database location: `fieldops-repo/data/fieldops.db`. `store.py` reads an optional `FIELDOPS_DB` environment variable to override the path, so tests use a temp file. Answer: default.
2. Crews: stay in `data/crews.csv`. `load_crews` is unchanged. Answer: default.
3. Rollback: a step-by-step note at the top of `scripts/migrate.py`. Stop the app, restore the old `store.py` from git, restart. `work_orders.csv` is never changed or deleted. The note says edits made after migration are not copied back to the CSV. No export command is added. Answer: default.
4. Re-running the migration: if `data/fieldops.db` already exists, the script stops with a clear message and changes nothing. The migration runs in one transaction, so a failure leaves no half-filled database. It prints only counts, never customer names or phone numbers. Answer: default.

## 4. Open questions

None.

## 5. Acceptance criteria

- Running `python scripts/migrate.py` from `fieldops-repo/` creates `data/fieldops.db` containing every order from the CSV file.
- The number of orders in the database equals the number of orders in the CSV file (40 today).
- `./run.sh` still shows the orders table, and assigning an order to a crew and closing an order still work.
- Running the migration a second time does not change or overwrite the existing database.
- The top of `scripts/migrate.py` has a rollback note with numbered steps for going back to the CSV file, and `data/work_orders.csv` is still present and unchanged after migration.

## 6. Test plan

All in `fieldops-repo/tests/test_store.py`, using a temp CSV and a temp database (via `FIELDOPS_DB`). Tests never touch the real data files.

- Criteria 1 and 2: run the migration on a copy of the CSV, then check that the database order count equals the CSV count and that ids, empty site values and priorities are kept.
- Criterion 3: `load_orders`, `get_order`, `update_order` (assign: crew and status; close: status) and `save_orders` return the same shapes as before (id and priority as integers, `get_order` returns None for an unknown id), and `load_crews` still returns crews with a list of skills.
- Criterion 4: a second migration run exits with a message and leaves the database rows unchanged.
- Criterion 5: after migration the CSV bytes are unchanged, and the first lines of `scripts/migrate.py` contain the rollback note.
- Manual check by the builder: `./run.sh` shows the table, then assign and close one order.

## 7. Work units

- fieldops-repo/fieldops/store.py: read and write work orders in SQLite; same function names; crews still from CSV.
- fieldops-repo/scripts/migrate.py: one-time CSV to SQLite migration, with the rollback note at the top.
- fieldops-repo/tests/test_store.py: tests for the criteria above.
- fieldops-repo/changes/KAN-158.md: change note for the PR.

## 8. Out of scope

- Moving crews to SQLite.
- Exporting the database back to CSV.
- Changes to `app.py`, `assign.py`, `nightly.py` or `report.py`.
- Deleting or editing `data/work_orders.csv`.
- New libraries (SQLite comes with Python's standard library).
- Updating the README text that mentions the CSV file.

## 9. Risk and compliance

- Personal data: orders hold customer names and phone numbers. The migration and tests print counts only. Any phone number shown in output is masked as 415-555-****.
- Secrets: none.
- Data loss: the CSV is kept, and migration refuses to overwrite an existing database. Edits made after migration live only in the database.
- Rollback: restore the old `store.py` from git and restart. Steps are in the note in `scripts/migrate.py`.
