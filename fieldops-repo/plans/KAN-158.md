## 2. What I understood
Work orders live in `data/work_orders.csv`. Every save rewrites the whole file, so two people saving at once can lose an edit. We move the orders to a SQLite database, `data/fieldops.db`, using a one-time script `scripts/migrate.py`. The screens, the assign and close actions and the nightly job must work the same, so the five functions in `fieldops/store.py` keep their names and return the same shapes. The CSV file stays in place as the way back, and a rollback note explains how to use it.

## 3. Design decisions
1. Database location and tests: default. The file is `fieldops-repo/data/fieldops.db`. `store.py` reads an optional `FIELDOPS_DB` environment variable and falls back to that path. Tests set it to a temp file, so real data is never touched. Changes: `store.py` and the tests.
2. Running the migration twice: default. If `data/fieldops.db` already exists, `migrate.py` stops with a clear message and changes nothing. Re-running can never wipe assignments or closures made after the first run. To migrate again, a person deletes the database file on purpose. Changes: `migrate.py` and a test for it.
3. Rollback and edits made after the move: default. The rollback note is at the top of `scripts/migrate.py`: stop the app, revert `store.py` with git, keep using `data/work_orders.csv`. The note says edits made in SQLite after the move are not copied back to the CSV. There is no export tool in this ticket. Changes: the docstring in `migrate.py` only.
4. Concurrent saves: default. `update_order` becomes one single-row `UPDATE` in a transaction, so assign and close no longer rewrite every order. `save_orders` (used by the nightly job) replaces all rows in one transaction. `crews.csv` stays as it is, because the ticket moves work orders only. Customer name and phone are copied unchanged. `*.db` is already in `.gitignore`, so the database is not committed. Changes: `store.py`.

## 5. Acceptance criteria
- Running `python scripts/migrate.py` from `fieldops-repo/` creates `data/fieldops.db` containing every order from the CSV file (40 today).
- The number of orders in the database equals the number of rows in `data/work_orders.csv`.
- `./run.sh` still shows the orders table, and assigning and closing an order still work and are still there after a reload.
- The top of `scripts/migrate.py` has a rollback note with numbered steps for going back to the CSV file, and `data/work_orders.csv` is not deleted or changed.
- Running the migration a second time does not change the database and tells the user why.
- `load_orders`, `save_orders`, `get_order`, `update_order` and `load_crews` keep their names and return the same data as before, including orders with an empty site or empty crew.

## 6. Test plan
All in `fieldops-repo/tests/test_store.py`, run with `.venv/bin/python -m pytest tests/test_store.py -v` from `fieldops-repo/`. Tests use a temp database and never print customer names or phone numbers.
- Criteria 1 and 2: run the migration against the real CSV into a temp database, then compare the row count with the CSV row count and check that all ids match.
- Criterion 3: `get_order`, `update_order` (assign sets crew and status, close sets status) and `load_orders` return the expected values and persist across a fresh call. Also check that `app.py` and `assign.py` still work through the store functions.
- Criterion 4: a test reads the top of `scripts/migrate.py` for the rollback note, and checks that the CSV file is unchanged after migration.
- Criterion 5: a second migration run leaves the database unchanged and reports a message.
- Criterion 6: orders 1035 and 1036 (empty site) and an unassigned order round-trip with the same field values, and `priority` and `id` are integers. `load_crews` returns the same crews as before.

## 8. Out of scope
- Moving crews to SQLite.
- Exporting from SQLite back to the CSV file.
- Deleting or changing `data/work_orders.csv`.
- Changes to the screens, `assign.py`, `nightly.py`, `report.py` or `app.py`.
- Adding any new package. Only the Python standard library `sqlite3` is used.

## 9. Risk and compliance
- Personal data: the orders hold customer names and phone numbers. They are copied unchanged. Logs, test output and chat must not print them. Phone numbers are shown as 415-555-**** if ever needed.
- Secrets: none.
- Data loss: the migration never overwrites an existing database and never touches the CSV file.
- Rollback: follow the note in `scripts/migrate.py`. Edits made in SQLite after the move are not copied back.
